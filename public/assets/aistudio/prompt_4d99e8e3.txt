PROJECT: BUILD A GAMIFIED 2D PHARMACY TRAUMA AND EMERGENCY SIMULATOR

1. Your role

Act as a senior full-stack developer, medical simulation engineer, clinical education specialist, UI/UX designer, game developer, and AI integration engineer.

Your task is to fully implement an interactive, gamified, 2D pharmacy trauma and emergency simulator inside my existing application.

This is an extension of my existing app, not a new application.

Before making changes, inspect the existing repository and understand its architecture, features, database, API integrations, and user progression systems.

The existing application already has a Learning tab that generates written clinical case studies. I want to preserve that functionality while building a substantially different experience in the Challenge tab.

The application uses my existing Grok API integration and has a clinical knowledge base that includes the Standard Treatment Guidelines (STG) and a drug list.

Reuse these resources wherever appropriate.

Do not replace existing functionality unnecessarily, introduce a competing user profile system, or rebuild unrelated parts of the application.

Primary objective

Build a mobile-friendly, two-dimensional interactive medical simulation where users can:

- Encounter visually represented patients.
- Examine injuries and recognize medical emergencies.
- Interact directly with patient illustrations.
- Select medical supplies and apply them to the appropriate body parts.
- Perform first-aid procedures in the correct sequence.
- Assess patients and make clinical decisions.
- Select medications and specify appropriate administration details when necessary.
- Experience simulated patient responses to their decisions.
- Complete time-sensitive emergency challenges.
- Receive detailed performance evaluations.
- Earn experience points, levels, and achievements.
- Improve their existing Identity Profile (IDP).
- Track their performance across multiple cases.

The finished experience must be functional, not merely a visual mockup.

Every interactive control must have a defined purpose, and the underlying application logic must respond appropriately to the user's actions.

5. Use a 2D interactive game engine

Build the simulator as a two-dimensional interactive experience using patient illustrations, clickable objects, selectable supplies, and visual treatment states.

Do not build a 3D environment.

Do not make the entire experience a sequence of multiple-choice questions.

The user must interact directly with the visual scenario.

Recommended visual implementation

Inspect the existing framework and select the simplest reliable approach that fits the project.

Depending on the existing architecture, suitable approaches may include:

- HTML, CSS, and JavaScript.
- SVG illustrations with interactive regions.
- Canvas-based rendering.
- An existing React-based interface, if the project already uses React.
- A lightweight 2D game library, if justified by the current architecture.

Do not introduce a large game engine unnecessarily.

The goal is a responsive 2D simulator that performs well on mobile devices.

Interactive patient scene

Each appropriate case should display a visual scene containing:

- The patient or patients.
- The affected body part.
- Visible symptoms or injury features.
- Relevant medical supplies.
- A patient information panel.
- A current objective.
- A progress indicator.
- A timer when appropriate.
- A contextual action panel.

The user should be able to tap interactive regions of the patient illustration.

For example, in a wound-care case, the affected leg or hand should be selectable.

Selecting an object should allow the user to perform a relevant action.

Where practical, support dragging supplies onto the correct body region. However, the essential functionality must also work through simple tap-to-select and tap-to-apply interactions.

Do not make drag-and-drop mandatory if it creates problems on small touchscreens.

Important implementation principle

The application must track what the user does, not merely what the user claims to have done.

If the user applies a dressing, the application must record that action and update the visual state.

If the user selects an inappropriate treatment, the application must record the error and apply the appropriate clinical and scoring consequences.

The visual scene, procedure state, clinical evaluation, and scoring system must remain synchronized.

8. Implement interactive trauma procedures

This is one of the most important features.

Trauma cases must contain practical procedures rather than merely describing what the user should do.

Example A: A patient with a cut on the leg

The application generates a case involving a patient with a cut on their leg.

The patient illustration shows the injury, and the user receives a concise description of what happened.

The available supplies appear in an interactive inventory.

Possible items include:

- Gloves.
- Sterile gauze.
- Appropriate wound-irrigation supplies.
- Dressings.
- Bandages.
- Plasters.
- Other suitable first-aid materials.

The available items should depend on the scenario.

Interactive workflow

Stage 1: Initial assessment

The user examines the injury and identifies the relevant findings.

The simulator evaluates whether the user recognizes the severity of the wound, assesses bleeding, and identifies signs requiring referral.

Stage 2: Select supplies

The user selects appropriate protective equipment and wound-care materials.

Stage 3: Perform wound care

The user selects an action and applies it to the appropriate area of the illustration.

For example, selecting a suitable irrigation action and applying it to an appropriate wound should update the simulated wound-care state.

Stage 4: Handle contamination

Where appropriate, the user identifies visible, accessible foreign material.

The simulator must not encourage dangerous exploration of deep wounds or removal of embedded objects that require professional assessment.

Stage 5: Control bleeding

The user performs appropriate bleeding-control actions.

The system must prioritize direct pressure and emergency escalation when indicated.

Stage 6: Apply a dressing

The user selects an appropriate dressing and applies it to the affected area.

The dressing should become visible in the updated illustration.

Stage 7: Determine the next action

The user decides whether the wound can receive pharmacy-level first aid or requires medical assessment or emergency transfer.

Stage 8: Complete the challenge

The application evaluates the entire procedure, including the actions performed, the sequence, omitted steps, unnecessary interventions, and critical errors.

Clinical requirements

Do not teach users to routinely pour hydrogen peroxide, alcohol, or other inappropriate substances into open wounds.

Use clinically appropriate wound-irrigation and dressing guidance.

Do not instruct users to close deep, contaminated, gaping, or otherwise unsuitable wounds in a pharmacy.

The correct sequence must depend on the actual wound and its severity.

Interactive feedback

If the user makes a mistake, provide feedback appropriate to the situation.

For a noncritical mistake, the application might indicate that the selected action is inappropriate and allow the user to reconsider.

For a critical emergency, the simulator should prioritize the required immediate action rather than forcing the user through every remaining interface step.

Do not reveal every correct answer immediately. The challenge should still assess the user's knowledge.

10. Implement time-sensitive emergency challenges

Some cases must involve time pressure.

Examples include:

- Anaphylaxis.
- Acute asthma exacerbations.
- Ongoing seizures.
- Severe bleeding.
- Other emergencies for which time-sensitive action is clinically justified.

Example B: Asthma attack

The application displays a patient experiencing breathing difficulty.

A visible countdown begins.

The user must assess the presentation, identify the severity, and select the appropriate immediate response.

Depending on the scenario, the user may need to:

1. Recognize the emergency.
2. Position or assist the patient appropriately.
3. Select the appropriate prescribed or protocol-authorized reliever treatment.
4. Follow verified medication administration guidance.
5. Assess the patient's response.
6. Escalate care when the patient is severely unwell or fails to improve appropriately.

The simulator must not reward an incorrect treatment simply because it was administered quickly.

Dynamic patient state

The application should track the simulated patient condition.

For example:

Initial presentation → User action → Safety validation → Simulated response → Updated patient condition

The outcome must depend on the clinical rules associated with the specific case.

An appropriate intervention may improve the simulated condition.

An ineffective intervention may fail to improve symptoms.

A dangerous intervention or delay may trigger deterioration when clinically justified.

The application must not claim that a particular treatment guarantees recovery.

Timer rules

The timer should reflect the urgency of the educational scenario.

Do not invent universal clinical deadlines.

When the timer expires, transition into the outcome and debrief stages.

The system should explain which essential actions were missed and why they mattered.

For real emergencies, actual emergency protocols always take precedence over game mechanics.

Emergency priority

Do not force users to complete unnecessary history-taking or administrative tasks while a patient needs immediate emergency intervention.

The interface should prioritize urgent actions.

Award bonus XP for appropriate, timely decisions.

Apply substantial penalties for critical errors, dangerous delays, and failure to recognize deterioration.

Speed alone must never be sufficient to earn a perfect score.

Other emergencies

Every emergency must have its own:

- Case definition.
- Expected actions.
- Critical safety rules.
- Appropriate timer, if needed.
- Outcome logic.
- Scoring rubric.
- Educational debrief.

13. Implement a reliable scoring engine

Create a structured scoring engine that evaluates the user's actual actions.

Every case must have a predefined scoring rubric before the user begins.

Do not allow Grok to invent the final score after seeing the user's answer.

Example scoring dimensions

Assessment dimension	Example weight

Recognition and assessment	20%
Diagnosis or clinical impression	15%
Immediate management	25%
Medication safety, when applicable	20%
Referral and follow-up	15%
Communication and patient safety	5%


These weights are examples, not fixed requirements for every case.

A trauma procedure may emphasize correct technique and sequencing.

Anaphylaxis may prioritize immediate management and emergency escalation.

A medication interaction case may emphasize medication safety and recognition of contraindications.

The rubric must adapt to the case.

Evaluate actual behavior

Track:

- Correct actions.
- Incorrect actions.
- Omitted actions.
- Actions performed in the wrong sequence.
- Unnecessary interventions.
- Incorrect medication selection.
- Incorrect doses.
- Contraindications.
- Drug interactions.
- Dangerous delays.
- Appropriate referral.
- Time taken, where relevant.

A user must not receive a perfect score by selecting the final correct answer after skipping essential steps.

Accept clinically equivalent answers and appropriate alternatives.

Performance bands

Below 50%: Critical failure

Show that the simulated management failed or that the patient deteriorated when clinically appropriate.

Explain the principal mistakes and show the correct management approach.

Allow the user to retry or start a new case.

50–79%: Partial success

Show what the user did correctly and what was missed.

The simulated patient may improve partially, remain unwell, or deteriorate depending on the case and the omitted interventions.

Explain the necessary corrections.

80–99%: Successful management with deficiencies

Show a generally successful outcome only when the essential safety requirements were satisfied.

Identify remaining omissions and risks.

Award appropriate XP, but do not award a flawless-performance badge.

100%: Flawless performance

Award a perfect score only when all required actions and safety checks have been completed correctly.

Grant the corresponding achievement if all badge requirements are met.

Critical safety overrides

A dangerous clinical error must override the aggregate score when appropriate.

For example, a user who identifies anaphylaxis but fails to initiate the required emergency response must not automatically receive a successful result because the remaining answers were correct.

Likewise, administering a dangerous contraindicated medication must trigger the relevant safety penalty.

Keep these metrics distinct:

- Numerical performance score.
- Critical safety errors.
- Simulated clinical outcome.
- XP earned.
- Category mastery.

This makes the results more meaningful than a single percentage.

14. Simulate patient outcomes realistically

The application must simulate the consequences of the user's decisions.

Possible outcomes include:

- Appropriate improvement.
- Full recovery within the limits of the scenario.
- Partial improvement.
- Persistent symptoms.
- Need for additional intervention.
- Adverse medication effects.
- Deterioration.
- Emergency escalation.
- Treatment failure.

Not every outcome is appropriate for every case.

For example, omitting a nonessential step during minor wound care should not automatically cause severe deterioration.

A dangerous error during anaphylaxis may have much more serious consequences.

Outcome calculation

Determine the outcome using:

1. The predefined case facts.
2. The user's recorded actions.
3. The validated scoring rubric.
4. Critical safety rules.
5. Verified medication and procedure requirements.
6. Clinically appropriate response rules.
7. Relevant time-sensitive factors.

Use deterministic application logic for the authoritative outcome.

Grok may provide the narrative explanation, but it must not freely decide the patient's fate without reference to the actual case rules.

Clearly label results as simulated educational outcomes.

Explain that they represent the scenario's programmed response and are not predictions of what would necessarily happen to a real patient.

21. Implementation process

Work directly in the existing repository.

Follow this sequence.

Phase 1: Inspect

Identify the existing architecture, Challenge tab, Learning tab, STG knowledge base, drug list, Grok integration, IDP, and persistence mechanisms.

Phase 2: Design the architecture

Determine how the application will represent patient cases, interactive actions, clinical rules, timers, scoring, patient states, and progression.

Define structured case data and validation rules.

Phase 3: Build the 2D interaction system

Implement patient illustrations, interactive injury regions, medical-supply inventories, tap-to-apply actions, and visual treatment states.

Phase 4: Build the clinical simulation engine

Implement the assessment workflow, procedure rules, medication checks, emergency timers, safety overrides, scoring, and patient-outcome calculations.

Phase 5: Integrate AI and clinical references

Connect case generation to the existing Grok API and validate generated cases against the available STG and drug database.

Phase 6: Implement gamification and IDP integration

Add XP, achievements, progression, case history, and persistent results using the existing profile system.

Phase 7: Build the debrief

Display scores, errors, clinical explanations, patient outcomes, rewards, and retry options.

Phase 8: Test and refine

Execute the test scenarios, fix identified problems, verify mobile interactions, and confirm that existing application functionality remains intact.

Work in manageable stages, but continue until the feature is implemented and tested as fully as the available environment permits.

Do not stop after creating a design mockup.

Do not leave essential buttons disconnected.

Do not substitute hardcoded scores for actual evaluation.

22. Final acceptance criteria

The Challenge tab is ready only when the following core experience works:

Select a challenge → Generate a valid case → Meet the patient → Inspect the situation → Gather information → Perform interactive first aid or emergency actions → Make appropriate clinical decisions → Select safe treatment where applicable → Simulate the patient's response → Receive a clinical debrief → Earn appropriate rewards → Update the existing IDP → Retry or continue.

Different cases may use different workflows, depending on their clinical requirements.

A minor cut should emphasize practical wound care.

A burn should emphasize appropriate burn first aid and severity assessment.

An asthma attack should emphasize timely recognition, appropriate treatment, and reassessment.

Anaphylaxis should prioritize immediate emergency management and escalation.

A medication emergency should emphasize safe medication decisions, contraindications, and relevant interactions.

Every case must remain clinically coherent and appropriately scoped for a pharmacy education simulator.

The ultimate goal is to transform the Challenge tab from a text-based question experience into a functional, visually interactive, 2D pharmacy emergency training game.

The simulator must reward clinical competence, make mistakes educational, provide realistic simulated consequences, and preserve the functionality of the existing application.
